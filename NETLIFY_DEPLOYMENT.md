# Netlify deployment

Netlify hosts only the frontend. Deploy Spring Boot separately on an HTTPS host and use persistent PostgreSQL. The `live` Spring profile requires database credentials, a JWT secret and an admin password; it disables demo data. Back up the database regularly and test restores. Preserve existing data and invoice sequences; do not reset the database or use ephemeral storage. Review and back up before applying the existing Flyway migrations to an existing database.

1. In Netlify, add a new project from Git and authorize GitHub. Select `zakaishere/marber-facture` and the branch you intend to deploy (normally your production branch). Merge the deployment changes into that branch first.
2. Netlify reads `netlify.toml`: base `frontend`, build command `node -e "const u = process.env.VITE_API_URL; try { if (!u || new URL(u).protocol !== 'https:') throw 0; } catch { console.error('VITE_API_URL must be an absolute HTTPS URL'); process.exit(1); }" && npm ci && npm run build`, publish directory `dist` relative to the base (`frontend/dist` from the repository root). Use these settings if prompted.
3. Set the Netlify build environment variable `VITE_API_URL` to the HTTPS origin of the deployed backend, for example `https://api.example.com` (no API path). It is embedded in public JavaScript: never put credentials or secrets in it. The build rejects a missing or non-HTTPS URL. Local development continues to use the existing Vite proxy when this variable is unset.
4. On the backend, set `SPRING_PROFILES_ACTIVE=live`, `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `APP_JWT_SECRET`, `APP_ADMIN_USERNAME`, `APP_ADMIN_PASSWORD`, and `APP_CORS_ALLOWED_ORIGINS`. Keep secrets in the backend host's secret settings. For example, set `APP_CORS_ALLOWED_ORIGINS=https://your-site.netlify.app` to the exact frontend origin, without a trailing slash. Multiple explicitly trusted origins may be comma-separated; avoid wildcards. Configure a strong unique JWT secret and password. Serve the backend over HTTPS.
5. Choose an available free `netlify.app` site name in Netlify site settings. Update the backend CORS origin if the name changes. Deploy previews use different origins and need explicit backend CORS entries if they must access the API.
6. Deploy the selected branch. After changing `VITE_API_URL`, trigger a new deploy (and clear the build cache if needed); Vite embeds the value at build time. Restart or redeploy the backend after changing its environment.

Example (placeholders only): frontend `VITE_API_URL=https://api.example.com`; backend `SPRING_PROFILES_ACTIVE=live`, `DB_URL=jdbc:postgresql://db.example.com:5432/marble`, `APP_CORS_ALLOWED_ORIGINS=https://your-site.netlify.app`. Supply the other backend secrets privately.

Troubleshooting: check the deploy log and lockfile if installation or build fails. Refreshing client routes is handled by the SPA rewrite; `/api/*` returns a 404 instead. API endpoints such as `/clients` overlap frontend routes, so API requests must go to the configured backend origin, never the Netlify origin. A CORS error requires the exact browser origin in the backend allowlist and a working HTTPS backend; check OPTIONS preflight and Authorization headers in browser developer tools. Mixed-content errors mean the backend URL is not HTTPS. For login failures, verify backend availability and credentials; for unexpected logout or 401, check token expiry, the JWT secret and backend time. Never share tokens, credentials, logs containing private data, or customer records when troubleshooting.

To move later, build the same frontend with `VITE_API_URL` set on the new host, serve `frontend/dist`, configure an SPA fallback and security headers there, and add the new exact origin to backend CORS. Update DNS and remove the old origin when no longer needed. No database migration is required to move the frontend.
